# 이 사업을 이해하는 순서

## 누구의 어떤 일을 돕는가

가정하는 고객은 반복 배송·취소 문의를 처리하는 소형 쇼핑몰 운영자다. 사용자는 상담원, 업무 승인자는 관리자다. 실제 구매 의사나 시장점유율을 조사해서 검증한 제품은 아니며 첫 비즈니스 학습 모델이다.

고객에게 제공하려는 가치는 ‘답변을 멋지게 작성’하는 데서 끝나지 않는다. 주문을 찾아 현재 상태를 확인하고, 처리 가능한 범위를 정하고, 예외를 맡길 사람을 정하고, 결과를 빠뜨리지 않는 일이다. 이 앱으로 그 흐름을 경험한다.

## 전체 업무

접수(문의 CSV/직접 입력) → 자료 찾기(주문 CSV) → 판단(학습용 정책) → 답변/승인/인계 → 모의 결과 기록 → 해결 → 통계/이력 → 자료 보존.

가상 자료로 먼저 ‘정상 상황’을 체험한 뒤 ‘실패와 예외’를 확인한다. 예외는 단순 오류 메시지가 아니라 업무 흐름의 일부다. 주문이 없으면 확인을 요청하고, 출고했으면 취소 경로를 막고, 담당자 인계 사유를 기록한다.

## 실습 6개

| 순서 | 과제 | 이해했는지 확인할 질문 |
|---|---|---|
| 1 | 배송 문의 생성·답변·해결 | 답변은 어떤 자료를 읽었고 실제 누구에게 전달됐는가? |
| 2 | 취소 요청·승인·실행 | 승인과 실행을 왜 분리했는가? |
| 3 | 승인 뒤 출고로 실행 차단 | 자료의 버전은 왜 저장했는가? |
| 4 | 고액 주문의 조건 제한과 인계 | 자동으로 하지 않을 업무는 어떻게 정하는가? |
| 5 | 이메일 불일치와 정보 노출 방지 | 이메일 비교와 본인 인증은 어떻게 다른가? |
| 6 | CSV 오류·중복·백업 | 코드 파일과 업무 자료는 어떻게 다른가? |

## ‘정식 사업’으로 검증할 때의 다음 질문

1. 실제 상담 담당자가 어떤 문의를 얼마나 자주 받는가? 개인정보를 제거한 표본을 통해 유형과 시간을 확인한다.
2. 현재 쇼핑몰·고객센터에서 이미 해결하는 기능과 해결하지 못하는 기능은 무엇인가?
3. 읽기 API와 쓰기 API에 접근할 권한이 실제로 있는가? 불가능하면 CSV 방식에도 효용이 있는가?
4. 누가 답변의 정확성과 취소 승인을 책임지는가?
5. 한 문의를 처리하는 시간·재문의 비율·오처리 비율이 달라지는가? 실제 전후 측정 없이는 절감 효과를 주장하지 않는다.
6. 월 구독·설정비·처리량 과금 중 실제 지불 의사와 비용 구조에 맞는 것은 무엇인가?

이 버전에는 매출 예측이나 임의 수익률을 대시보드에 넣지 않았다. 과금한다면 AI 호출·메시지·저장·고객 설정·지원·보안 운영 비용을 따로 계산해야 한다. 무료로 만든 시제품이라는 사실이 운영비가 없다는 뜻은 아니다.

## 학습 완료 조건

모든 코드를 외울 필요는 없다. 새 문의 한 건에 대해 ‘입력 자료 → 판단 조건 → 바뀐 상태 → 담당자의 다음 행동’을 설명하고, 잘못된 입력에서 왜 멈췄는지 설명하면 첫 단계는 달성한 것이다. 30개를 동시에 개발하지 않고 이 앱부터 한 흐름씩 실습한다.
